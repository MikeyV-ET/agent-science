# Agent Science

A framework for conducting reproducible science with AI agents.

## The Problem

When an AI agent conducts an experiment, and reaches a conclusion, the question of trust emerges. Can I trust the conclusion? Can I trust the data? What was the method? Can I trust the method?  Was this data actually generated by this method? The result is a set of findings that can't be independently verified, even when the underlying work is sound.

This is a tooling problem, but also a missing concept. The scientific community builds towards a paper using lab notebooks, datasets, code repositories, and papers. None of these are the right primary artifact for agent-driven science. An agents lab notebook isn't evidence. A dataset is the result of a process. And code only has meaning if what went in, came out, and the transformation of one to the other can be audited.  What's missing is an artifact that is:

- **Executable**: it contains complete instructions to reproduce a finding
- **Self-verifying**: running it confirms or falsifies the claimed result
- **Human-readable**: an expert can audit it without running anything
- **Agent-readable**: an agent can execute it without human intervention

We call this artifact an **experiment card**.

## The Core Test

> If a skeptical reader sees this card in the graph, does it give them enough information to verify the claim or reproduce the relevant result?

Every card type is judged by that bar:

| Card | Skeptical reader can… |
|------|------------------------|
| **Data** | Know what the artifact is, how it was made, and whether the hash matches |
| **Method** | Run the named map on a fixture and match the contract (not only hash the `.py`) |
| **Experiment** | Re-run the recipe on this item set (or audit it) and check outputs |
| **Hypothesis** | See the claim, the evidence ledger, and what would kill it |
| **Study** | See which cards and edges constitute the record (living card and/or snapshot) |

If the answer is no, the card is incomplete — add pins, hashes, method steps, discriminators, or schema until a skeptic could act without trusting narrative.

*(Core test formulation from Luna.)*

## The Core Idea: Experiment Cards

An experiment card is a recipe, not a report. It answers: "What is the finding, and what do I need to do to reproduce it: specifically?"

Every experiment card contains:

1. **Inputs** — everything that goes in, pinned by hash or reference. Data, models, configurations. Not descriptions of inputs — the actual inputs, or deterministic instructions to produce them.
2. **Method** — what to do with the inputs. Precise enough that execution is mechanical.
3. **Outputs** — what executing the method on the inputs produces. The claimed finding.
4. **Verification** — how to confirm the outputs match the claim. Usually: run the method, compare.

### Example: Evaluation Score

```yaml
card: antipattern-eval-NEW-2-grok43-s01
type: evaluation
brief_summary: |
  
inputs:
  question:
    content: |
      There are five houses in a row, each of a different
      color. In each house lives a person of a different
      nationality...
    hash: sha256:a3f2...
  subject_model: grok-4.3
  rubric:
    id: NEW-2
    content: |
      - **7**: Correctly identifies that the pet is missing...
      - **6**: Correctly identifies the missing pet...
      ...
    hash: sha256:b7c1...
  judge_model: sxs-claude-opus-4-6

method: |
  1. Send question to subject_model.
  2. Construct judge prompt from question + rubric + response.
  3. Send judge prompt to judge_model.
  4. Extract numeric score from judge response.

outputs:
  response:
    content: |
      The German owns the fish...
    hash: sha256:d4e5...
  judge_reasoning: |
    ## Scoring Analysis
    **Score: 6 — Correct**
    The model correctly identified that the puzzle states...
  score: 6

verification:
  joins_valid:
    question_in_judge_prompt: true
    response_in_judge_prompt: true
    rubric_in_judge_prompt: true
  reproducible: "Re-send judge prompt to judge_model; expect score 6"
```

## How Science Happens With an Agent

### The workflow

1. **Explore.** The agent and the scientist work together. Things break. Methods get revised. Wrong turns happen. The lab notebook captures this process. The exploration is valuable but the results are not canonical — they're preliminary.

2. **Hypothesize.** As patterns emerge from exploration, the agent and scientist articulate what they think is going on — as hypothesis cards. Each card names a specific, falsifiable claim, lists the evidence for and against, and identifies the discriminating observations that would eliminate it. This forces model-building to be explicit rather than implicit.

3. **Crystallize.** The exploration and hypothesis cards produce knowledge of what to test next. The agent and scientist distill this into **data cards** (frozen artifacts), **method cards** (named maps), **experiment cards** (recipes with pinned inputs/outputs), and a **study** (the DAG of those cards). A study is a **record**, not a target plan. Claimed experiment/data/method cards are not edited in place — mint a new version. A living study card may accrue new refs as cards are added; publishable snapshots are versioned (git tag / `studies/*.yaml`).

4. **Execute.** Run the recipe. This produces the canonical result — not the one from exploration, even if the numbers are identical. The recipe-produced result has full provenance and is independently reproducible.

5. **Update.** After execution, update hypothesis cards with new evidence. Move observations to `consistent_with` or `inconsistent_with`. Check discriminators against new data. Update status and strength. This closes the loop between experiment and theory.

6. **Verify.** Anyone (human or agent) can re-execute the recipe and confirm the result. Verification is computation, not judgment.

### Why first runs are throwaway

During exploration, the agent makes mistakes. Data lands in temp directories. Index mappings silently misalign. Scoring methods get changed mid-stream. The exploration run proves the *approach* works. The experiment card captures *how to do it right.* The canonical run from the card is the finding.

This is not how traditional science works. A bench scientist's first successful run IS the data (with replication for confirmation). But an agent's first run happens in a context window that will be compacted, using infrastructure that was built ad hoc, with verification that may be incomplete. The experiment card is what survives.

Sometimes you **cannot** throw the first run away: the mill already retried, the window is gone, the phenomenon will not recur. Then you mint **data cards from the blobs that exist** and write experiment cards whose method is “score these tapes,” with an explicit inclusion rule. The launch `n` is not the question. The study records that DAG. That is still crystallization — a record of what existed — not a pretend clean rerun.

### The notebook drives toward the card

The lab notebook is chronological, messy, and append-only. It records what happened, including wrong turns. The experiment card is clean, structured, and stable. It records what to do.

The notebook is not a lesser artifact — it's the record of the exploration that produced the card. But it is not the primary scientific output. The card is.

## Experiment Cards as Training Signal

An experiment card with a verified outcome is a training example with a ground truth endpoint.

Remove one component — say, the method — and the card becomes a test: "Given these inputs and this expected output, figure out the method." Remove the expected output: "Given these inputs and this method, what do you get?" Both are verifiable by execution.

This matters because current RL training for reasoning (GRPO, etc.) depends on verifiable endpoints. Math has calculators. Code has compilers. Scientific reasoning has no mechanical verifier — which is why frontier labs fall back on model-as-judge for non-verifiable domains.

Expert-validated experiment cards are verifiable endpoints for scientific reasoning. They're produced as a natural byproduct of expert-agent collaboration, not as an annotation task. The expert's motivation is the problem they're solving, not the training data they're generating.

At scale: one expert-agent collaboration produces one verified card. That card becomes N training examples by varying what's held out. Across a team of experts working real problems, thousands of verified cards accumulate. Each is a verifiable endpoint for a domain that currently has none.

## Format

Experiment cards are YAML files. YAML is:
- **Human-readable**: an expert can open the file and understand the experiment
- **Machine-parseable**: an agent can load the file and execute the recipe
- **Text-friendly**: block scalars (`|`) preserve long-form content (model responses, judge reasoning, methodology) as readable text within the structured format
- **Git-friendly**: diffs are meaningful, merges are possible

## Auditing

### Agent auditing
An agent verifies an experiment card computationally:
- Hash every input and output, compare to recorded hashes
- Verify all joins (do the inputs in the composition match the stored inputs?)
- Re-execute the method and compare outputs to claims
- Check completeness across a collection of cards

### Human auditing
A human audits by reading and navigating:
- Open a card, read the question/method/result
- Follow references to upstream cards (where did this input come from?)
- Follow references to downstream cards (where was this output used?)
- Spot-check specific entries — read the judge reasoning, evaluate whether the score makes sense

**Human reader (first pass):** structured HTML, expandable sections, **clickable full references** (card `id@version` → that card, named set → its table, method → `.py`). YAML stays the source of truth. If a reference cannot be clicked through to a real card or set, it is not a full reference.

**Agent reader:** parse the YAML, expand counted globs, hash blobs, re-run methods. Integrity highlighting (hash fail, `n ≠ 80`) belongs here, not in the first human pass.

**Open question:** SA (or similar) as the host for that HTML viewer.

## Hypothesis Cards

Experiment cards capture what happened. Hypothesis cards capture what you think is going on — and what would change your mind.

A hypothesis card is a structured bet: a specific claim, the evidence for and against it, and the discriminating observations that would eliminate it or its competitors. The key field is **discriminators** — each one names a concrete observation, says which hypothesis it would kill, and which it would support.

That field is also a **sentence type** in a writeup: *in order to eliminate the alternative that x is caused by y and not z, we performed the following experiment…* The experiment card is the recipe that sentence points at. Hypothesis cards are how you construct toward a conclusion, not only how you file a bet.

Hypothesis cards have a many-to-many relationship with experiment cards. One experiment may update several hypotheses. One hypothesis may draw evidence from many experiments.

**Full writeup:** [`hypothesis-card.md`](hypothesis-card.md)

## Data Cards

Experiment cards pin inputs and record outputs, but the same artifact
often plays both roles across a pipeline: a corpus is **data in** to a
probe; a `REPORT.md` is the **measurable out** of that probe and
**data in** to a comparison step.

A **data card** is a first-class primitive for any pinned artifact
(dataset, frozen prompt pack, report, index, imported weights). It
records identity (hash), provenance, schema, intended use, and
limitations — in the spirit of industry **dataset cards** / datasheets,
generalized beyond training data.

- **One type** of data card; **in** vs **out** are edges on the experiment
  DAG, not separate card species.
- Experiment cards should **reference** data cards (`data_card: id@version`
  + hash check) rather than re-describing large blobs in every recipe.
- Once a run claims an output hash, that data-card **version** is frozen.
  Next change = new version.

**Full writeup:** [`data-card.md`](data-card.md)

## Method Cards

Experiment cards pin a recipe for **one trial**. Data cards pin **bytes**.
A **method card** pins a **transformation**: what goes in, what comes out,
how to invoke the code, and a `check` a skeptic can run on a fixture.

Hashing the `.py` (a data card of the file) is identity. The method card
is the contract of the map. Experiment cards **reference** method cards
rather than restating numbered steps. `invoke` may show a default item
set; the scientific question stays on the experiment.

When many artifacts share a role (eighty session tapes), describe a
**set** (directory, glob, `n`). Edges point at the set. Placeholders and
N copy-pasted edges both fail a skeptic.

**Full references.** A card points at another card by **id** (and
`@version` once claimed), or at a **named set** with glob and `n`. Not
`D-<uuid>`. The human reader turns those ids into clickable links. The
agent reader expands the set and checks the count. A placeholder cannot
be hashed or opened.

**Full writeup:** [`method-card.md`](method-card.md)

## Versioning: Cards and Studies

**Editing a card in place** destroys the recipe behind past results.
**Versioning a card** keeps every claimed run answerable.

| Layer | What | Rule |
|-------|------|------|
| Artifact bytes | `sha256` of content | Hash change ⇒ different artifact |
| Card revision | Experiment / hypothesis / data card `version` | Immutable once a clean run claims it; next change mints `@n+1` |
| Study / DAG | Named bundle of card versions + edges | The **publishable unit** — not a mutable folder name |

Drafts may be mutable (`status: draft` / `wip/`). After first claimed
execution, treat the card revision as an immutable recipe. The set of
cards and the DAG that connects them is itself versioned (study
snapshot / git tag).

**Full writeup:** [`versioning.md`](versioning.md)

```
  data-card.md

```

One `cards/` pile buries eighty data cards next to two experiments.
Species folders keep the graph audible. Do not name a folder `inputs/`
for that reason — in vs out are DAG edges.

## Status

This framework is in early development. It emerged from a concrete failure: an anti-pattern evaluation experiment where data was lost, indices misaligned, and results had to be re-run — all problems that a recipe-first approach would have prevented.

The concept has been tested against three projects of different shapes:
- **Anti-pattern eval** (evaluation scoring: question → response → judge → score)
- **Sub-vocal desire detection** (multi-stage training: build → probe → preserve)
- **Interleave GRPO** (batch measurement + training: curriculum across difficulty levels)

The experiment card structure generalizes across all three. **Data cards** and **card/study versioning** were added as co-equal primitives (see `data-card.md`, `versioning.md`). **Method cards**, living **study** records, and minting data cards from a sitting you cannot rerun were added from SciCode-Verified 34.1 / grok-4.6 (see `method-card.md`). Implementation and tooling are next.
